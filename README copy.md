# User Management API

A small Express REST API used to test automatic documentation-drift detection. It uses hardcoded in-memory user records, so data resets whenever the server restarts. The API listens on port `3000` by default; the `PORT` environment variable can override this value.

## Run the API

Install Express with `npm install express`, then start the server with `node app.js`.

## Data model

Each user has an integer `id`, a non-empty `name`, an `email` address, a `role`, and an `active` boolean. The supported roles are `student` and `admin`. Email addresses must be valid and unique, with uniqueness checked without regard to letter case. User IDs are generated by taking the largest existing ID and adding one.

The initial in-memory data contains three users: Aarav Sharma (ID 1), Diya Verma (ID 2), and Kabir Mehta (ID 3).

## Endpoints

### GET `/`

Returns HTTP `200` with an API welcome message and version string.

### GET `/api/health`

Returns HTTP `200` with `status: "ok"` and the process uptime in seconds.

### GET `/api/users`

Returns HTTP `200` with a JSON object containing `success`, `count`, and `data`. The `data` property is an array containing every user currently in memory, and `count` is the number of users in that array.

### GET `/api/users/:id`

Returns HTTP `200` with the requested user inside the `data` property. The ID must be a positive integer. A malformed or non-positive ID returns HTTP `400`, while an ID that does not identify a user returns HTTP `404`.

### POST `/api/users`

Creates a user and returns HTTP `201` with a success message and the created user inside `data`. The request body must contain a non-empty string `name` and a valid `email`. `role` defaults to `student`, and `active` defaults to `true`. A supplied role must be `student` or `admin`, and a supplied `active` value must be a boolean. Invalid input returns HTTP `400`. An email already used by another user returns HTTP `409`.

### PUT `/api/users/:id`

Completely replaces the editable fields of an existing user and returns HTTP `200` with the updated user inside `data`. The request body must contain all four fields: `name`, `email`, `role`, and `active`. The name must be a non-empty string, the email must be valid and unique, the role must be `student` or `admin`, and active must be a boolean. Invalid IDs or request data return HTTP `400`. A missing user returns HTTP `404`, and a duplicate email returns HTTP `409`. The user's ID cannot be changed through this endpoint.

### PATCH `/api/users/:id`

Partially updates an existing user and returns HTTP `200` with the updated user inside `data`. The request body may contain one or more of `name`, `email`, `role`, and `active`; omitted fields retain their previous values. An empty body, an unsupported field, or an invalid supplied value returns HTTP `400`. A missing user returns HTTP `404`, and an email already used by another user returns HTTP `409`. The user's ID cannot be changed through this endpoint.

### DELETE `/api/users/:id`

Removes the requested user from the in-memory array and returns HTTP `204` with an empty response body. A malformed or non-positive ID returns HTTP `400`; a user that does not exist returns HTTP `404`.

## General behavior

Unknown routes return HTTP `404` with a JSON message. The API uses JSON request bodies for POST, PUT, and PATCH. Changes are stored only in memory and are not persisted to disk or a database.

## Documentation drift detector

The reusable engine is in `drift-engine.js`. It exports `analyze({ diff, docs, originalCode, updatedCode, codeFile, callModel, modelOptions })`; `docs` accepts a string or an array of `{ file, content }` objects. The result separates `findings` from `suggestions`. Model suggestions are explicitly unverified. This fixture intentionally removes `success` and `count` from GET `/api/users` in `app.js` while the README still documents them; this is the sample drift under test. The API smoke test checks the current response shape and preserves that deliberate mismatch. The current deterministic rule catches documented JSON response fields removed from an Express route; it uses Markdown endpoint headings such as `### GET /api/users` as route context and returns exact changed-line evidence.

Run the documentation checker with `npm run check-docs` after committing a baseline for `app.js`. It compares the committed and current source and prints the engine result. Ollama is configured with `OLLAMA_MODEL`, `OLLAMA_URL`, and `OLLAMA_NUM_CTX`; the default model is `qwen2.5-coder:7b`. When there are no changed lines, the model is not called.

For integration with another backend:

```js
const { analyze } = require('./drift-engine');
const result = await analyze({
  diff,
  docs: [{ file: 'README.md', content: readmeText }],
  originalCode,
  updatedCode,
  codeFile: 'app.js',
  modelOptions: { model: 'qwen2.5-coder:7b', numCtx: 8192 }
});
```

Run the focused engine checks with `npm run test:engine`, the API checks with `npm run test:api`, or both with `npm test`. The live Qwen 2.5 Coder 7B run on 21 scenarios scored 4/21 exact case passes. Claim-detection F1 was 0.833, but exact-evidence F1 was 0.222, so model suggestions remain unverified. See `evaluation/README.md` and `evaluation/results.md` for expected versus actual output for every case. Run `npm run evaluate` to repeat the model simulation; the command exits nonzero if any case fails.
